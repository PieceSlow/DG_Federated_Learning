# 16 · 本机模型 20 人批次实验记录

> 目的：记录接入本机 Ollama（`--llm ollama`）后，用 **qwen3:8b** 在真实 MIMIC-IV 数据上跑
> 20 人队列的结果，并与同一队列的确定性运行（`--llm off`）逐项对比，说明差异、本次接入的
> 价值边界，以及接下来的方向。
>
> 一句话结论：**结构一致、产物一致，但对象携带的字段与敏感级别并不一致**；
> 本次接入的价值在"验证可替换性 + 压测校验/回退链 + 暴露既有缺陷"，不在提升产物。

## 4. 与基线的差异

### 4.1 完全相同的部分

| 项 | 说明 |
|---|---|
| 对象类别 | 都是 8 类（7 类业务对象 + 派生 Concept 1,254 个） |
| 关系与边行数 | 9 类，`108 / 27 / 1,571 / 4,267 / 142 / 35` + 概念边 `1,571 / 4,267 / 142` |
| 图谱校验问题 | 都是 0 |
| KV 标签 | 34,634 条 / 18 个 tag_key |
| 概念覆盖率 | 100%（图谱命中 99.9%） |
| `clinical_events` | 6,015 行，列差异 0 |

### 4.2 不同的部分：对象携带的字段

按 `graph/nodes.parquet` 里**实际落库**的属性列对比（不是提案原文）：

| 对象 | 基线属性 | 智能体属性 | 差异 |
|---|---|---|---|
| Patient | `subject_id, gender, anchor_age, anchor_year` | 同 + `anchor_year_group` | 多 1 列 |
| **Encounter** | `hadm_id, admittime, dischtime, admission_type, hospital_expire_flag` | 同 **去掉 `hospital_expire_flag`**，多 `insurance / marital_status / race` | **丢了住院死亡标志** |
| ICUStay | `stay_id, intime, outtime, first_careunit, last_careunit` | 同 + `los` | 多 1 列 |
| **ClinicalNote** | `note_id, charttime, note_type` | **只有 `note_id`** | **丢掉时间与文书类型** |
| **Diagnosis** | 含 `subject_id` | **缺 `subject_id`**（键退化为 `hadm_id + seq_num + icd_code`） | **主键弱化** |
| Prescription | `pharmacy_id, starttime, drug, formulary_drug_cd, dose_val_rx` | 同 + `drug_type, dose_unit_rx, route` | 多 3 列 |
| **Procedure** | 含 `subject_id` | **缺 `subject_id`** | **主键弱化** |

三处需要注意：

1. **`hospital_expire_flag` 丢失**——这是住院死亡标签，也是本项目（联邦 ICU 死亡率预测）的
   目标变量。现在没出问题，只是因为 `patient_360.mortality` 直接读 `admissions` 表，不读图谱。
2. **ClinicalNote 丢掉 `charttime` / `note_type`**——模型提了个源表里不存在的列名 `note_text`，
   `_node_frame` 按"列必须存在"静默过滤，于是只剩主键 `note_id`。
   好处是"没让不存在的列进图"，代价是"没报错，也没补齐"。
3. **Diagnosis / Procedure 的主键少了 `subject_id`**——本队列里
   `hadm_id + seq_num + icd_code` 恰好唯一，所以通过了"主键唯一"校验；
   但主键语义已从"患者内唯一"退化为"住院内唯一"。

### 4.3 不同的部分：敏感级别（方向危险）

| 对象 | 基线 | 智能体 |
|---|---|---|
| **Patient** | **L3**（仅本地） | **L1**（可公开） |
| **ClinicalNote** | **L3** | **L1** |
| Encounter | L3 | L2 |
| ICUStay | L3 | L2 |
| Diagnosis / Prescription / Procedure | L2 | L2 |

模型把**患者对象与临床文书降了两级**。在医疗数据治理里这是最不能出错的方向。
级别由模型自选（提示词只给了 `L1/L2/L3` 三档，没有规定每个对象该是哪档），
说明它没有把"人口学 + 文本可重识别"这条风险纳入判断。

### 4.4 为什么下游产物仍然一致

因为消费链**不读图谱的属性与级别**：

- `label` 阶段给 Patient 打 `L1.sensitivity` 时用的是固定值（`_patient_frame` 里写死 `"L3"`），
  事件级级别来自 `event_type → L2/L3` 映射，**都不读图谱**；
- `classify` 读的是标签里的 `L1.sensitivity`，**不读图谱**；
- 图谱的 `sensitivity` / `attributes` 只落到 `metadata/object_graph.json`、
  `metadata/object_inventory.csv` 和节点属性 JSON 里。

所以"产物一致"是**下游尚未消费这部分信息**的结果，不是"两种建模等价"的证明。
一旦有人把分级或特征抽取接到图谱上，4.2 与 4.3 的差异就会直接变成数据质量问题。

## 5. 本次接入的价值

需要分清"已经拿到的"和"还没拿到的"。

### 5.1 已经拿到的

1. **验证了建模环节可替换**：在只有 schema / 统计视图、不含任何患者行的条件下，
   模型产出了与人工 `objects.yaml` **结构等价**的 8 类对象 / 9 类关系，
   且通过了"源表存在、主键在列里、主键唯一、join 列存在"的全部校验。
   这是换医院、换表结构时"能不能不靠人重写对象模型"的可行性证据。
2. **压测了校验与回退链**：多次运行中，模型的异常输出（键名 `source,table`、
   截断的 `"source,"`、`target_table` 填成源表名、`on` 键在 YAML 里被解析成布尔、
   结构漂移成 `{name, description, primary_key}`）都被拦下并回退，交付产物一次未被污染。
3. **暴露了 4 个与模型无关的既有缺陷**：`LLMRequest.schema` 从未发给模型、
   YAML 把 `on` 解析成布尔导致 schema 字段名变成 `"true"`、校验器驳回理由不进重试反馈、
   agent 抛异常绕过重试。前两个对云端接口同样存在。
4. **保留了确定性默认**：`--llm off` 仍是默认路径，模型是可选增强，不影响交付。

### 5.2 还没拿到的（也是"等价"含金量有限的原因）

1. **对象识别被提示词写死**。[object_finder.yaml](governance/prompts/object_finder.yaml) 直接规定
   "必须把下面 7 类对象全部提出（缺一不可）"，并给出 `name / source_table` 对照，
   甚至连主键组合都写了（`diagnoses_icd` 要带 `seq_num + icd_code`）。
   关系抽取同样固定了 6 个关系名与方向。模型做的是**按图填表**，不是**发现对象**；
   因此"结构等价"有相当部分是**按构造**得到的。
2. **对齐侧表达力不足**：模型给的是"每目标一条"（8 条），表达不了"每目标 × 每事件源表"
   的 1:N（匹配器是 38 条），只能作旁证。
3. **校验器限制了模型的合理提议**：`on` 必须是**源对象的主键**，所以"诊断 → ICD 字典"
   这类编码连接会被直接驳回；模型即便提出这类关系也用不上。

## 6. 接下来的方向

按优先级排列，前两步不完成，接入模型就没有生产价值。

### 第一步：让图谱的属性与级别闭环（最高优先）

- 分级改为读图谱对象的 `sensitivity`，并加一条硬约束：
  **图谱级别不得低于该对象事件级的级别**，模型一降级就报错；
- 属性加入列存在性校验：模型提出的 `note_text` 这类不存在的列要**报错**而不是静默丢弃；
- 把基线属性当作必填清单（`hospital_expire_flag`、`charttime`、`note_type` 不得缺），
  缺失即驳回并带反馈重试。

验收：20 人队列上，智能体版与基线的对象属性、级别**逐项相等**；故意让模型漏字段时能被拦下。

### 第二步：放开提示词的硬清单

- `object_finder` 只给"表 / 列 / 统计 / 约束（主键唯一、字典表不作对象、labevents 不进图谱）"，
  **删掉 7 类对象与主键写法的清单**；
- `relation_extractor` 只给"关系的语义与约束（`on` 必须是 `from` 的主键）"，
  删掉固定关系名。

验收：给出模型自主提出的对象/关系与人工 `objects.yaml` 的差异清单（多了什么、少了什么、
为什么），并在多份数据（不同 cohort、不同中心）上重复，而不是单次单队列。

### 第三步：补齐表达力

- 对齐结果支持"每目标 × 每事件源表"，让智能体的映射能真正进入 `field_level.csv`；
- 校验器支持字典 / 编码连接（`on` 不必是源主键，只需两侧都有该列且基数合理），
  这样模型提出的"诊断 → ICD 字典"关系才可用；
- 把 `GraphCritic` 的建议从 `agent_trace.jsonl` 提到报告产物里，成为可读的审阅意见。

验收：智能体映射与匹配器映射做差异比对、进入人工 review 队列；关系提案的命中率与驳回率可统计。
