# 05 · 对象化与标签化

## 1. 对象化：从"表"到"对象"

对象化的价值是给数据一个**业务语义的骨架**：谁是谁、谁属于谁、以什么键关联。有了这层骨架，
编目、共享、联邦建模才有共同语言。

### 1.1 7 类 MIMIC 对象 + 1 类派生概念对象

| 对象 | 主键 | 粒度 | 敏感级别 | 行数（本队列） |
|---|---|---|---|---|
| Patient | `subject_id` | 1 行/患者 | L3 | 100 |
| Encounter | `hadm_id` | 1 行/住院 | L3 | 350 |
| ICUStay | `stay_id` | 1 行/ICU 停留 | L3 | 126 |
| ClinicalNote | `note_id` | 1 行/出院小结 | L3 | 155 |
| Diagnosis | `subject_id + hadm_id + seq_num + icd_code` | 1 行/诊断 | L2 | 5,319 |
| Prescription | `subject_id + hadm_id + pharmacy_id + drug` | 1 行/处方 | L2 | 18,384 |
| Procedure | `subject_id + hadm_id + seq_num` | 1 行/操作 | L2 | 696 |
| Concept（派生） | `cui`（命中 UMLS）/ `code_system+code`（未命中的兜底） | 1 行/概念 | L1 | 2,259（CUI 2,039 + 编码级 220） |

**主键必须能区分"一行数据"。** `diagnoses_icd` 的 `seq_num` 会重复（同一住院同一序号下
有多条诊断码），`prescriptions` 的一个 `pharmacy_id` 下会有多个药品组分——只用
`subject_id+hadm_id+seq_num` / `+pharmacy_id` 做键，会把不同的行并成同一个对象，图谱里
出现重复 `object_id`（20 人真实队列 489 个重复：处方 486、诊断 3）。所以诊断键带上
`icd_code`、处方键带上 `drug`；`graph.verify` 新增 `GRAPH_DUPLICATE_NODE`（error）守这条不变量。

**Concept 是真实节点，不是"文档里的第 8 类"**。概念层只有一条规则：事件节点 →
`concept_key.ConceptResolver` 解析 CUI；**命中就用 CUI 合并**（`source_table=concept_map`），
**未命中就建编码级兜底节点**（`source_table=clinical_events`）。解析器按事件类型对齐体系名
（诊断 `ICD{v}`、操作 `ICD10PCS/ICD9CM_PROC`、处方按药名查 `RXNORM`），图谱和标签调的是同一个
解析器和同一个主键函数（`concept_key.concept_object_id`），所以两边的概念键从构造上一致。

实测（100 人，UMLS 2026AB）：2,259 个概念节点（CUI 2,039 + 编码级 220），标签里 2,260 个
概念对象中 2,259 个能在图上找到（差 1 条文书概念，概念表里没有文书映射）。

### 1.2 6 条结构化关系 + 3 类概念边（每条落一张边表）

```text
Patient ─1:N─ Encounter ─1:N─ ICUStay
                  ├─1:N─ ClinicalNote
                  ├─1:N─ Diagnosis
                  ├─1:N─ Prescription
                  └─1:N─ Procedure

Diagnosis / Prescription / Procedure ─1:N─ Concept（UMLS CUI）
```

### 1.3 产物

- `output/governance/metadata/object_graph.json`：对象、键、属性、行数、关系（类型级）；
- `output/governance/metadata/object_inventory.csv`：扁平的清单，便于放进表格或报告；
- `output/governance/graph/nodes.parquet`：**节点实例**（`object_type / object_id / attributes`，
  含 UMLS `Concept` 节点）；
- `output/governance/graph/edges/<relation>.parquet`：**每种关系一张边表**
  （`src_id / dst_id / relation / evidence / confidence`），
  含 `diagnosis_concept` / `prescription_concept` / `procedure_concept`；
- `output/governance/graph/graph_manifest.json`：对象/关系计数与来源（不含患者行，可公开）。

**为什么边当表存。** 边不是画在图上就完事：它要能被查询（"某患者的所有就诊与诊断"就是 join）、
能带属性（证据、置信度、时间）、能增量追加（新数据进来 append），还要能被下游工具直接读取。
每种关系一张 parquet，既满足这些要求，又不必为课程作业部署图数据库。

### 1.4 图谱由智能体链条构建（可回退）

`--llm mock/api` 时，建图走智能体链条：

```text
ObjectFinderAgent（schema/统计视图 → 对象候选）
   │ 校验：源表存在、主键在列里（不通过 → 带反馈重试）
   ▼
RelationExtractorAgent（对象定义 → 关系候选）
   │ 校验：join 列必须存在（不通过 → 重试）
   ▼
本地 build_graph（执行定义，生成节点/边）
   ▼
GraphCriticAgent（看图谱统计 → 缺陷建议 → 必要时回退重抽关系）
```

`--llm off`（默认）时回退到 `objects.yaml` 的确定性模型，保证可复现；
每次智能体调用写 `output/audit/agent_trace.jsonl`，可追溯"谁提了什么、谁驳回了什么"。
**动态构建**：`--graph-mode incremental` 按主键 upsert 节点与边，保留未出现的旧数据，
`graph_history.jsonl` 记录每次运行的 `delta`（added/updated/unchanged/removed）；
默认 `full` 模式整图重建，保证同一输入可复现。`--graph-delete-missing` 可显式清理过期数据。

对象图谱的类型级描述（`object_graph.json`）只有结构与计数，定级 L1；
节点/边实例含患者标识，属 L2/L3，只在本地 `output/` 中保存、不提交。

## 2. 标签化：对象上的 KV 断言

标签不是"多算几个字段"，而是**打在数据对象上的 KV 断言**，用于检索、筛选、管控与业务决策。
判定三条：是判定/结论（不是原始测量值）、打在某个对象上（能回答"打在谁身上"）、有业务用途。

### 2.0 标签建在图谱之上

标签阶段依赖 `clinical_events` 与 `graph` 两个前置产物，`ctx.graph` 是完整的
`GraphData`（节点 + 边），因此标签可以直接走图，而不是回去对宽表再数一遍：

| 标签输入 | 图谱口径 | 回退口径 |
|---|---|---|
| 住院级处方/诊断/操作条目数 | `edges["has_prescription"/"has_diagnosis"/"has_procedure"]` 按 `src_id` 计数 | 源表 `groupby("hadm_id").size()` |
| `L4.comorbidity_burden` | `Patient → Encounter → Diagnosis` 两跳后按 ICD 章节去重 | 事件表 `icd_chapter.nunique()` |
| `L3.*` 概念标签 | 概念主键与图谱 Concept 节点同源 | 事件表 `(code_system, code)` |

两种口径同时计算：图谱口径生效，表口径作为基线对账；不一致时产出
`LABEL_GRAPH_MISMATCH`（只报行数，不报患者标识），防止口径在后续改动中悄悄漂移。

### 2.1 四层标签

| 层 | 打在谁身上 | 回答的问题 | 典型来源 |
|---|---|---|---|
| **L1 资产级** | 数据集/表 | 这份数据能怎么用 | 规则/定义 |
| **L2 记录级** | 事件、住院、患者记录 | 这是什么、可不可信 | 字段、规则 |
| **L3 概念级** | 术语/编码（Concept） | 术语怎么理解、能否跨体系 | 字典、UMLS |
| **L4 断言级** | 患者 × 时间 × 事件 | 临床事实是什么 | 规则、NLP、聚合 |

### 2.2 表结构

`output/governance/labels/object_labels.parquet`：

`object_type / object_id / tag_key / tag_value / layer / source / confidence / evidence / version / computed_at`

`output/governance/labels/tag_dictionary.csv` 记录每个 `tag_key` 的定义、层、口径、来源与计数；
`output/governance/quality/label_coverage.json` 记录 Event/Patient/Concept 的标签覆盖率。

### 2.3 首批标签

| 层 | tag_key | 对象 | 口径 |
|---|---|---|---|
| L1 | `L1.sensitivity` | Event/Patient/Dataset | L2/L3 |
| L1 | `L1.sharing_boundary` | Dataset | controlled / aggregate_only |
| L2 | `L2.entity_class` | Event | Diagnosis/Procedure/Prescription/ClinicalNote |
| L2 | `L2.time_precision` | Event | datetime/date/null |
| L2 | `L2.missing_reason` | Event | no_source_field/non_numeric |
| L2 | `L2.assertion` | Event | present/negated/hypothetical/historical/family（文书规则抽取，取最强） |
| L2 | `L2.certainty` | Event | definite/possible（hypothetical、family 视为 possible） |
| L2 | `L2.elderly` / `L2.long_stay` / `L2.icu_long_stay` | Patient/Encounter/ICUStay | 年龄、住院/ICU 天数 |
| L3 | `L3.code_system` / `L3.semantic_type` / `L3.cui` | Concept | 编码体系、UMLS STY、CUI |
| L4 | `L4.comorbidity_burden` / `L4.polypharmacy` / `L4.frequent_admitter` / `L4.drug_intensity` | Patient | 章节数、药品数、住院次数、用药强度 |
| L4 | `L4.polypharmacy_encounter` / `L4.high_followup_priority` | Encounter | 处方条目、随访优先 |

断言维度在本数据集里很稀疏：`L2.assertion` = present 24,548 / historical 4 / negated 2，
`L2.certainty` 全为 definite（文书里没有"疑似"表述）。维度已建、可继续扩规则，但数据本身
罕有否定/疑似，是数据侧局限。

阈值口径（代理指标）：`L4.polypharmacy` 为跨住院去重药品种类 ≥40，`L4.frequent_admitter`
为住院次数 ≥3，`L4.polypharmacy_encounter` 为单次住院处方条目 ≥5；不是临床诊断标准。

### 2.4 与"医学标签强化"的边界

- **标签化**：L1–L4 全部 KV 标签，是数据治理的语义层；
- **医学标签强化**：只指 L3 概念级（`L3.cui`、`L3.semantic_type`、同义词归一），
  由 `concept_map`（UMLS）提供。已接入 2026AB：编码映射覆盖率 **84.3%**
  （ICD10 99.6% / ICD9 94.4% / ICD10PCS 99.4% / ICD9CM_PROC 60.4% / RXNORM 88.8% /
  LNC 39.8%），`L3.cui` **2,039 条**；未命中的编码降级为 ICD 章节（不含 CUI）。

定义在 `governance/labels/definitions.yaml`（版本化），计算在 `labels/engine.py`，
输出 `output/governance/labels/object_labels.parquet`；支持 `--manual-labels` 手动覆盖，
对应笔记里"手动标签是把隐性知识显性化"。

### 2.5 ICD 章节映射

ICD-10 按首字母归章（A/B 传染病、C/D 肿瘤、I 循环、J 呼吸……），`H` 段特殊处理：
`H00–H59` 归眼科、`H60–H95` 归耳科。ICD-9 按数字区间归章（1–139 传染病……800–999 损伤）。
无法识别时给 `Unknown`（空编码）或 `Other / unclassified`（未知段），不留空串——
空串在后续统计里会被误当成缺失值。

### 2.6 敏感级别与对象类型

| 对象类型 | 级别 | 依据 |
|---|---|---|
| 诊断 / 操作 / 处方 | L2 | 健康状态敏感，但结构化、已编码 |
| 临床文本 | L3 | 自由文本含叙述性隐私，可推断身份与事件 |
| 人口学 / 就诊 | L3 | 年龄+性别+时间轴可辅助重识别 |

同一患者在不同表里可能被标成不同级别（例如人口学 L3、诊断 L2），因此**行级敏感级别取该行所属对象的级别**，
患者 360 则取最高级别 L3。这条规则写死在 `assemble` 里，避免各处自行判断；分级结果里
对应 `C08 患者级视图 / L3`，与标签 `Dataset:patient_360 = L3` 一致。

## 3. 与分类分级的关系

标签化负责"打上语义与级别"，分类分级负责"把它变成制度"：每类数据怎么用、谁能看、
去标识到什么程度、能共享到什么边界。详见 `06-分类分级与编目.md`。

## 4. 局限

- ICD 章节只是粗粒度语义，不能替代临床分类（如 DRG）；
- 没有 SNOMED/LOINC 等更细的术语标签；
- 文本没有做 PHI 重识别风险评估，因此整体按 L3 处理。
