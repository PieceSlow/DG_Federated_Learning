# 10 · 字段对齐与标签最终口径（2026-11-18）

> 与旧文档的区别：**33 条静态映射已删除**；字段对齐改为 schema matching；
> 聚合/派生字段不再混入对齐表；标签改为对象级 KV。

## 1. 字段对齐

### 1.1 目标 schema

`governance/alignment/target_schema.yaml` 定义 8 个由源字段直接提供的目标字段：

`subject_id、hadm_id、stay_id、event_time、code、display、numeric_value、text_value`

每个目标声明 `dtype / required / source_tables / source_fields`。`source_fields` 是**声明式契约**：
哪些源字段可以供给这个目标字段。

### 1.2 匹配与选择

```text
源字段（类型/空值率/基数）
  × 目标（8 个）
  → name / type / structure / value 四个匹配器
  → 加权组合（0.45/0.25/0.15/0.15）
  → 每个「目标字段 × 源表」取 top-3（不是每个目标字段只取 top-3）
  → 声明的源字段直接准入；未声明的按 阈值 0.5 + 类型族过滤
  → field_level.csv（status=auto/review，method=matcher/declared，带 evidence）
```

三条口径必须讲清楚：

1. **选择粒度是「目标字段 × 源表」**。`subject_id` 在 8 张源表里都有，若只按目标字段取
   top-3，`diagnoses_icd.subject_id` 会被 `patients.subject_id` 挤出候选，下游按事件类型
   生成 SQL 时就取不到字段。按源表各取最优，才是一张可用的字段映射表。
2. **声明过的字段不因阈值被否掉**。`target_schema.yaml` 的 `source_fields` 是对齐契约，
   匹配器负责打分排序、给 `status`，而不是否决契约（例如 `formulary_drug_cd → code`、
   `dose_val_rx → numeric_value` 字面不相似，但确实是正确来源）。这类行 `method=declared`，
   靠匹配器自身达标的行 `method=matcher`。
3. **源表时间列在接入阶段统一成 datetime**（`ingest.coerce_times`）。否则
   `procedures_icd.chartdate` 是字符串、目标 `event_time` 是 datetime，类型匹配器判为
   不兼容，正确字段反被类型约束挡掉。

- `status=auto`：within-table rank 1、score ≥ 0.7、类型兼容；其余为 `review`；
- 不计算 precision/recall，因为没有 gold；评价指标是覆盖率、必填覆盖、review 数。

### 1.3 派生/聚合字段

`mapping/derived_fields.csv` 记录**不参与匹配**的字段：

- `clinical_events`：record_id、event_type、code_system、source_table、source_record_id、split、sensitivity、icd_chapter；
- `patient_360`：n_admissions、n_icu、total_los_days、mortality、first_admit、last_discharge、n_diagnosis、n_procedure、n_prescription、n_notes、text_chars、top_diagnosis、top_drug 等。

这些字段写输入、公式、用途，避免再把聚合当成"字段对齐"。

### 1.4 MEDS 接口交叉表

`mapping/field_level_meds.csv` 由 `crosswalk.py` 读取 `meds_targets.yaml` 生成：
9 类事件 × 5 个核心字段（45 行）。它是接口对照，不是匹配结果。

### 1.5 组织汇聚 SQL：对齐结果的下游消费者

`mapping/build_clinical_events.sql` 由 `alignment/sql.py::build_sql_with_usage(field_map)`
**用字段映射生成**，不是另写一套规范：

| 来源 | 含义 | 例 |
|---|---|---|
| `mapping:` | 目标字段 ← 匹配到的 (源表, 源字段) | `t.icd_code AS code`、`d.long_title AS display` |
| `transform:` | 一对多转换 | `dose_val_rx+unit+route → text_value` |
| `spec` | 事件规范常量 | 文书 `code='DISCHARGE'` |
| `derived` | 由事件规范生成 | `record_id`、`code_system`、`sensitivity` |
| `missing` | 该事件类型确实没有这个字段 | `Diagnosis.event_time`（诊断无发生时间） |

`quality/sql_execution_report.json` 里的 `mapping_usage` 记录每个事件类型每个字段的来源，
汇总成 `mapping / transform / spec / derived / missing` 五类计数。**这就是"字段映射被谁用了"
的答案**：SQL 生成 → 内存 SQLite 执行 → 与 `assemble` 的事件表对账行数与类型分布。

## 2. 标签

`labels/object_labels.parquet` 是对象级 KV：

`object_type / object_id / tag_key / tag_value / layer / source / confidence / evidence / version / computed_at`

### 2.1 标签建在图谱之上

`label` 阶段声明依赖 `clinical_events` **和 `graph`**（`pipeline.STAGES`），
`compute_labels(..., graph=ctx.graph, issues=...)` 直接读图谱：

| 标签 | 图谱口径 | 回退口径 |
|---|---|---|
| `n_diagnoses` / `n_prescriptions` / `n_procedures`（L4 的输入） | `graph.edges["has_diagnosis"]` 等按 `src_id` 计数 | 源表 `groupby("hadm_id").size()` |
| `L4.comorbidity_burden` | 两跳：`Patient ←has_encounter→ Encounter ←has_diagnosis→ Diagnosis`，按 `icd_code/icd_version` 算章节去重 | 事件表 `icd_chapter.nunique()` |
| `L3.code_system` / `L3.semantic_type` / `L3.cui` | 概念主键与图谱 Concept 节点同源（`concept_key.concept_object_id`） | 事件表 `(code_system, code)` |

两条口径同时计算：**图谱口径生效，表口径作为基线对账**。不一致时产出
`LABEL_GRAPH_MISMATCH`（warning，只报行数不报患者标识），避免口径悄悄漂移。

### 2.2 Concept 主键统一

`concept_key.concept_object_id(code_system, code, cui)`：**有 CUI 用 CUI（`Concept:{cui}`），
没有 CUI 用编码（`Concept:{编码体系}:{编码}`）**。图谱 Concept 节点与标签 Concept 对象
都调用这个函数，两边的对象因此可以 join；`label_coverage.json` 的
`Concept.graph_nodes / graph_matched` 就是这条一致性的度量。

没有 UMLS 时图谱也会建**编码级降级概念节点**（`graph.build.build_concept_layer`），
否则"图里 0 个概念对象、标签里 5,784 条概念标签"仍然对不上。

| 层 | 代表 tag_key |
|---|---|
| L1 | `L1.sensitivity`、`L1.sharing_boundary` |
| L2 | `L2.entity_class`、`L2.time_precision`、`L2.missing_reason`、`L2.elderly`、`L2.long_stay`、`L2.icu_long_stay` |
| L3 | `L3.code_system`、`L3.semantic_type`、`L3.cui` |
| L4 | `L4.comorbidity_burden`、`L4.polypharmacy`、`L4.frequent_admitter`、`L4.drug_intensity`、`L4.polypharmacy_encounter`、`L4.high_followup_priority` |

- `labels/tag_dictionary.csv`：定义、层、口径、来源、计数；
- `quality/label_coverage.json`：Event/Patient/Concept 覆盖率；
- 阈值：`L4.polypharmacy` ≥40（本数据集代理口径）、`L4.frequent_admitter` ≥3、
  `L4.polypharmacy_encounter` ≥5。

## 3. 标签化 vs 医学标签强化

| 概念 | 范围 | 落点 |
|---|---|---|
| 标签化 | L1–L4 全部 KV | `labels/`、`label.py` |
| 医学标签强化 | L3 概念级：CUI、语义类型、同义词 | `L3.cui` / `L3.semantic_type`，由 `concept_map`（UMLS）提供 |

没有 UMLS 时：`L3.semantic_type` 降级为 ICD 章节，不生成 `L3.cui`；UMLS 由组员负责，
代码只消费 `output/governance/concept/concept_map.parquet`。
此时图谱的 Concept 节点同样降级为编码级节点（`source_table=clinical_events`），
保证"概念对象在图上真实存在"。

## 5. 验收

- `field_level.csv` 不含 `n_*`、`total_los_days`、`top_*`；
- `field_level.csv` 每个「目标字段 × 源表」都有候选，`method ∈ {matcher, declared}`；
- `derived_fields.csv` 覆盖这些聚合/派生字段；
- 8 个目标中 `subject_id`、`code` 必填且被覆盖；
- `build_clinical_events.sql` 里 `AS code` / `AS event_time` 等表达式来自映射，
  `mapping_usage.summary.mapping > 0`；`missing` 只应包含该事件类型确实没有的字段；
- `field_level_meds.csv` 45 行，9 类事件 × 5 字段；
- `object_labels` 含 L1–L4，`L2.time_precision=null` 与事件时间空值数一致；
- 标签的 Concept 对象键 ⊆ 图谱 Concept 节点键（无 UMLS 时除文书概念外全覆盖）；
- `LABEL_GRAPH_MISMATCH` 无告警（图谱与表口径一致）；
- 测试：`python -m unittest discover -s tests -t .`（197 个）。
