# 03 · 质量校验与事件仓储

## 1. 两层校验

### 1.1 规范层（失败即终止）

| 校验 | 时机 | 失败后果 |
|---|---|---|
| `MEDS DataSchema.validate`（内存核心列） | 03 校验 | 立即终止 |
| `MEDS DataSchema.validate`（写盘后读回） | 04 仓储 | 立即终止 |
| `MEDS CodeMetadataSchema.validate` | 04 | 立即终止 |
| `MEDS SubjectSplitSchema.validate` | 04 | 立即终止 |
| `MEDS DatasetMetadataSchema.validate` | 04 | 立即终止 |
| `subject_id` 有序性 | 04 | 立即终止 |

"写完再读回校验"是刻意的：内存里对、磁盘上错（编码、类型、排序）只有读回来才暴露。

### 1.2 业务层（写问题清单，不静默修正）

| 规则 | 级别 | 触发条件 | 处理 |
|---|---|---|---|
| `CODE_FORMAT` | error | 编码不符合 `命名空间//值` | 事件被阻断 |
| `CODE_MAPPING` | warning | 缺 `formulary_drug_cd` 等映射键 | 不输出该事件，留痕 |
| `CODE_NOT_IN_DICTIONARY` | warning | 编码/项目号不在字典中 | 保留事件，标记 |
| `OBJECT_ASSOCIATION` | error | `hadm_id`/`stay_id` 不在对象中 | 置空外键，保留事件 |
| `TEMPORAL_INCONSISTENCY` | warning | 出院早于入院、事件超出住院窗口 | 保留原文，标记 |
| `DUPLICATE_EVENT` | warning | 同源记录完全重复 | 保留第一条 |
| `MEDS_REQUIRED_FIELD` | error | `subject_id` 或 `code` 为空 | 阻断 |

明细写入 `output/governance/quality/issues.csv`，同一规则最多保留 200 条明细（`ISSUE_CAP_PER_RULE`），
但计数不截断——避免问题文件无限膨胀，同时不丢规模信息。

图谱阶段还会追加一组跨表一致性规则（`source_table=graph`）：

| 规则 | 级别 | 含义 |
|---|---|---|
| `GRAPH_DANGLING_EDGE` | error | 边的端点不在节点集合中（外键指向不存在的对象） |
| `GRAPH_ORPHAN_NODE` | warning | 患者/住院/ICU 节点没有任何关系 |
| `GRAPH_MISSING_RELATION` | warning | 诊断/处方/操作/文书未挂到住院上 |
| `GRAPH_TEMPORAL_CONFLICT` | warning | 出院早于入院、出科早于入科、ICU 窗口超出住院窗口 |

**为什么只标记不改写**：出院带药、入院前用药、跨院检查都是真实临床情况。把它们"修正"到住院窗口内
会制造假数据，破坏可审计性。治理的目标是让问题**可见**，而不是让报表好看。

## 2. 事件仓储结构（MEDS）

```text
eventstore/
├── data/events.parquet                  # 核心 5 列 + 6 扩展列
└── metadata/
    ├── codes.parquet                    # code / description / parent_codes
    ├── subject_splits.parquet           # train / tuning / held_out
    └── dataset.json                     # 数据集元数据
```

| 扩展列 | 作用 |
|---|---|
| `hadm_id` / `stay_id` | 对象关联，联邦侧可按就诊聚合 |
| `source_table` / `source_record_id` | 记录级血缘（`表名:行号`、`discharge:note_id`） |
| `mapping_version` | 映射版本，换规则时可区分历史产物 |
| `extractor` | `structured` / `note_rules:v1`，标明事件由谁生成 |

`dataset.json` 声明 `raw_source_id_columns` 与 `other_extension_columns`，让下游知道哪些列是
原生标识、哪些是扩展列——这是跨中心交换时最容易出问题的地方。

## 3. 患者划分

按 `sha256("split-v1:" + subject_id)` 取模 100：`<70` train、`<85` tuning、其余 held_out。
确定性、与文件名无关、同一患者在事件仓储、事件表、患者 360 中划分一致。

## 5. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `未找到 MIMIC-IV 数据目录` | 路径未配置或挂载失败 | 用 `--mimic-root` 或 `MIMIC_ROOT` |
| `缺少依赖 langgraph` | 未装依赖 | `pip install -r requirements.txt` |
| schema 校验失败（类型） | pandas dtype 推断差异 | 检查 `meds.py` 的显式 schema，不要依赖自动推断 |
| 内存不足 | 队列过大 | 调小 `--cohort-size` |
