# 04 · 汇聚与字段对齐

## 1. 汇聚：统一事件表 `clinical_events`

诊断、操作、处方、文书四类记录来自不同表、不同粒度、不同时间字段，统一成一行一条事件：

| 源表 | 粒度 | `event_type` | 时间字段 | 编码体系 |
|---|---|---|---|---|
| `diagnoses_icd` | 1 行/诊断 | Diagnosis | 无（留空） | ICD9 / ICD10 |
| `procedures_icd` | 1 行/操作 | Procedure | `chartdate` | ICD9 / ICD10 |
| `prescriptions` | 1 行/处方 | Prescription | `starttime` | MIMIC_FORMULARY |
| `discharge` | 1 行/小结 | ClinicalNote | `charttime` | MIMIC_NOTE |

字段：`record_id / subject_id / hadm_id / stay_id / event_type / event_time / code_system /
code / display / numeric_value / text_value / icd_chapter / source_table / source_record_id /
split / sensitivity`。

`record_id` 用前缀 + 源主键生成（`DX:`、`PX:`、`RX:`、`NOTE:`），保证同一源行稳定唯一。

### 1.1 关联原则

| 难点 | 处理 |
|---|---|
| 同一概念字段名不同 | 由匹配器按 name/type/structure/value 打分，不按字段名硬套 |
| 时间字段来源不一 | 统一转 timestamp；诊断无时间留空，不臆测 |
| 粒度不同 | 统一成事件粒度，用 `record_id` 前缀区分 |
| 关联键缺失 | `hadm_id` 可空；孤儿计入质量报告，不静默丢弃 |
| ICU 挂接 | 只有落在 `[intime, outtime]` 内才挂 `stay_id` |

### 1.2 ICU 挂接的上限

诊断没有时间，处方只有 `starttime`，因此只能按窗口挂接。本队列挂接 10,533 条（42.9%）。
这是**方法上限**而不是漏做：没有更细的时间信息，就无法判断某条处方是否发生在 ICU 内。

## 2. 汇聚：患者 360 宽表

一行一名患者，列包括：

| 组 | 列 |
|---|---|
| 人口学 | `gender`、`anchor_age`、`anchor_year`、`subject_id` |
| 就诊 | `n_admissions`、`n_icu`、`total_los_days`、`mortality`、`first_admit`、`last_discharge` |
| 事件计数 | `n_diagnosis`、`n_procedure`、`n_prescription`、`n_notes`、`text_chars` |
| 标签 | `top_diagnosis`、`top_drug` |
| 治理 | `split`、`sensitivity` |

`patient_360` 是**资源视图**，其中的 `n_*`、`total_los_days`、`top_*` 是聚合/派生字段，
不属于"字段对齐"；它们统一登记在 `mapping/derived_fields.csv`。

## 3. 字段对齐：schema matching（无静态映射表）

### 3.1 目标 schema

`governance/alignment/target_schema.yaml` 只列**由源字段直接提供**的 8 个目标字段：

| 目标字段 | 类型 | 必填 | 允许的源表 |
|---|---|---|---|
| `subject_id` | int64 | 是 | patients/admissions/icustays/diagnoses/procedures/prescriptions/labevents/discharge |
| `hadm_id` | int64 | 否 | admissions/icustays/diagnoses/procedures/prescriptions/labevents/discharge |
| `stay_id` | int64 | 否 | icustays |
| `event_time` | timestamp | 否 | admissions/icustays/procedures/prescriptions/labevents/discharge |
| `code` | string | 是 | diagnoses/procedures/prescriptions/labevents/discharge |
| `display` | string | 否 | d_icd_diagnoses/d_icd_procedures/d_labitems/prescriptions |
| `numeric_value` | float | 否 | labevents/prescriptions/icustays |
| `text_value` | string | 否 | discharge/prescriptions/labevents |

派生字段（`record_id`、`event_type`、`code_system`、`source_table`、`source_record_id`、
`split`、`sensitivity`、`icd_chapter`）由代码生成，**不参与匹配**，见 `derived_fields.yaml`。

### 3.2 四个匹配器

| 匹配器 | 依据 | 说明 |
|---|---|---|
| `string` | 字段名规范化（camel/snake 拆分、后缀+同义词）+ 编辑距离 | `label/title/display/drug` 归一为 `label` |
| `type` | 类型族（int/float/time/text） | int/float 视为兼容 |
| `structure` | 共同 token / `_id`、`_time`、`_code` 后缀 | 同后缀加分 |
| `value` | 本地聚合统计（类型族 + 空值率） | 不发送取值 |

加权组合（0.45/0.25/0.15/0.15）后，每个目标字段保留 top-3、阈值 0.5，并过滤类型不兼容的
候选；允许 1:N（同一目标字段由多个源字段提供，如 `code` 来自诊断/操作/处方）。

### 3.3 输出与复核

`mapping/field_level.csv` 每行给出：

`target_table / target_field / target_dtype / required / source_table / source_field /
source_dtype / score / string_score / type_score / structure_score / value_score / rank /
method / status / evidence`

- `status=auto`：rank 1、score ≥ 0.7、类型兼容；
- `status=review`：其余候选，交人工复核；
- `alignment_report.json`：目标覆盖、必填覆盖、auto/review 数量、缺失必填项；
- 不再计算 precision/recall，也不存在 33 条 gold。

### 3.4 MEDS 交叉表（另加）

`mapping/field_level_meds.csv` 由 `crosswalk.py` 读取 `meds_targets.yaml` 生成：
9 类事件 × 5 个核心字段（45 行），用于检查对外接口字段是否有源字段可落；
它是接口对照，不是匹配结果。

### 3.5 SQL（可选）

`build_sql()` 按四类事件的固定规范生成 `build_clinical_events.sql`，用 SQLite 对账
行数与类型分布；SQL 不依赖字段映射表。

## 4. 记录级血缘

`record_level.parquet` 为每条数据集记录登记来源：

- `clinical_events` → `source_table` + `source_record_id`（可回到原始行）；
- `patient_360` → `derived:patient_360:<subject_id>`（**subject 级血缘**）。

聚合行无法一对一落到单条源记录，因此不伪造映射，而是在血缘里标明"派生"。

## 5. 实测（100 人真实队列，2026-11-18 复跑）

| 项 | 数值 |
|---|---|
| 统一事件表 | 24,554 行（处方 18,384 / 诊断 5,319 / 操作 696 / 文书 155） |
| 患者 360 | 100 行 |
| 记录级映射 | 24,654 条（24,554 事件 + 100 患者行） |
| ICU 挂接 | 10,533 条（42.9%） |
| 匹配目标 | 8 个源字段；必填 2 个 |
| 字段映射 | 38 条（31 matcher / 7 declared；22 auto / 16 review） |
| SQL 对账 | 执行 24,554 行，四类事件行数与事件表一致（`status=ok`） |
| SQL 字段来源 | mapping 19 / transform 1 / spec 2 / derived 32 / missing 10 |
| 未匹配（`missing`） | 10 个，全部是该事件类型确实没有的字段：`stay_id`×4、`event_time`（诊断）、`numeric_value`×3、`text_value`×2 |

`missing` 里没有一个是"该有却没找到"：`stay_id` 只有 `icustays` 提供，而四类事件表
都不是 ICU 表；诊断没有发生时间；文书/诊断没有数值。这是**如实记录缺口**，
而不是用常量把 NULL 填成看似完整。

## 6. 局限

- 纯规则匹配，同义字段（如 `long_title`→`display`）依赖同义词表，仍可能落 review；
- 没有人工标注，覆盖率不等于准确率，review 项必须人工确认；
- 处方编码不是药物本体（未映射 RxNorm/ATC）；
- ICD 章节只是粗粒度语义，不能替代临床分类。
