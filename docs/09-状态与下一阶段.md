## 4. 字段对齐设计（2026-11-18）

```text
源字段视图（类型/空值率/基数）
   × 目标 schema（8 个源字段，按事件类型限定允许源表与可接受源字段）
   → name / type / structure / value 四个匹配器
   → 加权组合（0.45/0.25/0.15/0.15）
   → 每个「目标字段 × 源表」top-3 + 声明字段直接准入 + 类型过滤
   → field_level.csv（auto/review + method=matcher/declared）
   → build_clinical_events.sql（用映射生成）→ SQLite 对账 → mapping_usage
   → alignment_report.json（覆盖/必填/复核）
```

- 目标字段：`subject_id`、`hadm_id`、`stay_id`、`event_time`、`code`、`display`、
  `numeric_value`、`text_value`；`record_id`、`event_type`、`split` 等是派生字段，不匹配；
- **选择粒度是「目标字段 × 源表」**：`subject_id` 在 8 张表里都要留一条，
  否则按事件类型生成 SQL 时字段会缺一半；
- **`source_fields` 是契约**：声明过的字段不被阈值/类型过滤否掉（`method=declared`），
  匹配器负责打分排序与 `status`；
- **SQL 是映射的下游消费者**：`sql.py::build_sql_with_usage(field_map)` 逐字段解析
  `mapping / transform / spec / derived / missing` 五类来源，写进
  `sql_execution_report.json.mapping_usage`；
- 目标 schema：`governance/alignment/target_schema.yaml`；
- MEDS 接口台账：`field_level_meds.csv`（10×5，回填匹配结果与 `resolved_by`）；
- 派生/聚合：`derived_fields.csv`，例如 `n_admissions`、`total_los_days`、`top_drug`；
- 不再有 `_field_map()`、33 条 gold、`field_level_reference.csv`、`LEGACY.md`。

## 4.1 MEDS 接口：声明驱动 + 落地台账（2026-11-18）

```text
meds_targets.yaml（10 类事件 × 5 个 MEDS 核心字段，每列写 source）
  → standardize 按 table/emit_if/template/time/numeric/text 产出事件
  → interface.check_events：命名空间是否都声明过、必填列是否真的非空
  → crosswalk：声明 × field_level.csv → field_level_meds.csv（50 行）
  → meds_interface_report.json：resolution / undeclared / required_violations
```

- 字段来源四类：`spec`（模板/常量，`uses` 指明吃哪些源列）、`derived`（直接取源行列）、
  `mapping`（必须由匹配提供）、`none`（确实没有，必须写 `note`）；
- 落地结果五类：`resolved_by ∈ {mapping 24, spec 7, derived 1, none 18, unmapped 0}`；
- 声明与实现的一致性由测试守着：模板占位符必须在 `uses` 里、`join` 必须写 `on_column`
  （YAML 1.1 会把裸 `on:` 解析成布尔）、`source` 引用的列必须真的在已接入表里存在；
- 修掉的历史不一致：`DIAGNOSIS.time` 声明 required 却一直发 NULL（改为按 `admittime` 兜底）、
  `DEMOGRAPHIC` 发了但没声明、`LAB.code` 模板与实际编码不同、`MEDICATION.numeric_value`
  声明了剂量却发空（现在按 `dose_val_rx` 落地、区间剂量落 NULL）。

## 4.2 标签建在图谱之上（2026-11-18）

- `label` 阶段依赖 `clinical_events` + `graph`；`ctx.graph` 是完整 `GraphData`
  （nodes/edges），不再只有类型级 `object_graph`；
- 住院级 `n_diagnoses / n_prescriptions / n_procedures` 读边表计数；
  `L4.comorbidity_burden` 走 `Patient→Encounter→Diagnosis` 两跳、按 ICD 章节去重；
- 概念对象主键由 `concept_key.concept_object_id` 统一：有 CUI 用 CUI，无 CUI 用编码；
- 无 UMLS 时图谱也建**编码级降级概念节点**，避免"图里没有概念、标签里 5,784 条概念标签"；
- 图谱口径与表口径同时算，不一致产出 `LABEL_GRAPH_MISMATCH`（只报行数）。

## 9. 已知问题（诚实清单）

1. **`procedures_icd` 不在 MEDS 接口里**：操作只在 `clinical_events`（Procedure 事件）中，
   接口声明里没有 PROCEDURE 命名空间；这是作业范围（9 类事件）导致的选择，已在
   `meds_targets.yaml` 的 `source_gaps` 写明补法（`PROCEDURE//ICD{version}//{code}`）；
2. **38 条字段映射只有 19 条被 SQL 消费**：`patients/admissions/icustays/labevents/d_labitems`
   不产出 `clinical_events` 的 4 类事件，它们的映射行是"契约候选"。`field_level.csv`
   的 `consumed` 列如实标出，覆盖率因此不能当"用上了"读；
3. 匹配器是规则型，`display`←`long_title` 等同义字段依赖同义词表，仍会落 review；
4. `catalog.py` 仍引用 `patient_360`；
5. 没有人工标注，无法给出准确率，只能给覆盖率与复核量；
6. 真实 API 只做过 tiny smoke，不代表模型质量；本次交付统一 `--llm off`；
7. 无 UMLS 时图谱只有**编码级**概念节点，不能合并同义词、无概念关系；
8. `LABEL_GRAPH_MISMATCH` 只在图谱与表口径同时可算时产生，不是全量断言；
9. `TEXT_*` 规则明细按 200 条/规则封顶，计数不封顶（本次 `TEXT_DRUG_MISMATCH` 计 246、明细 200）；
10. 字段映射 38 条里 16 条为 `review`，尚未人工复核；接口台账里对应 6 列
    `mapping_status=review`，同样待确认；
11. **检验文本结果未接入**：`ingest` 只取 `valuenum/valueuom/flag`，没有取自由文本 `value`，
    所以 `LAB.text_value` 在接口里声明为 `none`；要补文本结果需要改接入列并评估敏感级别；
12. **诊断时间用住院时间兜底**：MEDS 的 `DIAGNOSIS.time` 取 `admittime`，不是诊断发生时刻
    （诊断本身没有时间）；汇聚层 `clinical_events.Diagnosis.event_time` 仍然留空。
