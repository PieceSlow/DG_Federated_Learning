# 01 · 总体设计

## 1. 为什么要做成一条流水线

早期脚本分成两段：一段做"事件流标准化"，一段做"资产化治理"。当成两个独立程序维护时，
代码能跑，但讲不清一个关键问题：**一份数据从原始表到可以对外共享的资产，中间经历了什么、
每一步的判断依据是什么**。

所以这个仓库按治理环节组织：每个环节是一个阶段，有自己的输入、判断规则、产物和审计记录。
阶段之间用同一个运行上下文串起来，于是"哪一步、处理了多少条、产生几条告警、耗时多少"
都能在一份 `audit_log.csv` 里对上。

## 2. 场景：多中心联邦学习

多家医院在不共享原始病历的前提下共同训练模型。这对本地治理提出三条硬约束：

| 约束 | 治理动作 | 本系统的落点 |
|---|---|---|
| 口径必须跨中心一致 | 统一事件标准与编码规范 | MEDS 事件仓储、`命名空间//值` 编码 |
| 每条数据要能回溯 | 记录来源表、来源行、住院号 | `source_record_id`、`hadm_id`、`stay_id`、记录级映射 |
| 敏感数据不出本地 | 分级、访问控制、共享边界 | 分类分级 + 五级目录 + 敏感级别标签 |

## 3. 架构

```text
                 ┌──────────────────────────────────────────────┐
 MIMIC-IV ──────►│ 01 接入     02 标准化     03 校验    04 仓储  │──► eventstore/（MEDS）
 MIMIC-Note ────►│   │            │            │          │     │
                 └───┼────────────┼────────────┼──────────┼─────┘
                     │            │            │          │
                     ▼            ▼            ▼          ▼
              GovernanceContext（tables / events / issues / audit / stats）
                     │
                 ┌───┴──────────────────────────────────────────┐
                 │ 05 汇聚  06 对齐  07 概念归一  08 对象化      │──► governance/（资产）
                 │ 09 标签化  10 分级  11 编目  12 报告          │
                 └──────────────────────────────────────────────┘
```

**为什么用 LangGraph。** 阶段之间是明确的先后依赖，天然适合用有向图表达。用图编排的好处是：
每个节点只关心自己的输入输出、可以单独重跑（`--stages`）、失败时能定位到具体节点；而把逻辑写进
一个 800 行的 `main()` 里，任何一步出错都只能靠打印语句排查。

**为什么所有阶段共享一个上下文。** 统计口径、问题清单、审计日志必须全局唯一。否则
"事件数"在报告里和落盘文件里可能对不上，这在数据治理里是硬伤。

## 4. 阶段依赖

| 阶段 | 依赖 | 说明 |
|---|---|---|
| 01 接入 | — | 产出 `tables`、`cohort` |
| 02 标准化 | `tables`、`cohort` | 产出 `events`（含对象索引） |
| 03 校验 | `events` | 清洗、去重、schema 校验 |
| 04 仓储 | `events` | 写 MEDS 并读回复验 |
| 05 汇聚 | `tables`、`events` | 产出 `clinical_events`、`patient_360` |
| 06 对齐 | 上面两张表 | 字段级、记录级映射 |
| 07 概念归一 | `tables` | ICD/药品/检验 → UMLS 概念（缓存缺失则跳过） |
| 08 对象化 | `tables` | 对象模型、节点/边实例与图谱 |
| 09 标签化 | `clinical_events` | 标签体系与标签清单 |
| 10 分级 | 两张表 | 规则与结果 |
| 11 编目 | 两张表 | 五级目录 |
| 12 报告 | 两张表 | 质量汇总 |

阶段编号即执行顺序；`run.py --stages` 只跑子集时，依赖不满足会立刻报"缺什么"。

## 5. 两个"数据产品"的边界

| | 事件仓储 `output/eventstore/` | 治理资产 `output/governance/` |
|---|---|---|
| 消费者 | 联邦学习训练侧、跨中心对齐 | 本地数据管理、审计、共享审批 |
| 结构 | MEDS 规定的目录与列 | 自定义：数据集/映射/对象/标签/分级/目录 |
| 稳定性 | 受官方 schema 约束，变更需评估兼容性 | 随治理需求演进 |
| 敏感级别 | L2/L3 混合 | 以 L1 元数据为主，数据集部分 L2/L3 |

把两者分开是有意的：对外接口要稳定，内部资产要灵活。混在一起会让"哪些能给外部"变得含糊。

## 6. 口径一致性

- 队列：`icustays` 中 `subject_id` 最小的 N 名，确定性、可复现；
- 划分：按 sha256 稳定划分 70/15/15（train/tuning/held_out），同一患者在所有产物里划分一致；
- 时间窗：住院 `[admittime, dischtime]`、ICU `[intime, outtime]`，越界只标记不改写；
- 文本：每份小结截断到 20,000 字符，报告里明确标注"截断"而非全文。

这些口径在实现上只有一处定义（`meds.subject_split`、`quality` 的时间窗判断），避免各阶段各算一套。

## 7. 扩展点

| 想改什么 | 改哪里 |
|---|---|
| 换队列策略（如按诊断筛选） | `ingest.run` 中队列构造 |
| 增加源表 | `ingest.run` 读取 + `standardize._map_structured` 映射 |
| 换文本抽取器（如接 LLM） | `standardize._extract_text` 中的抽取函数，只要返回 `{code, text_value}` |
| 增加质量规则 | `quality._check_events` + `ISSUE_CAP_PER_RULE` 说明 |
| 调整敏感级别 | `label.SENSITIVITY` 与 `classify.RULES` 同步 |
| 换事件标准（非 MEDS） | `meds.py` 的 schema 与落盘函数 |
