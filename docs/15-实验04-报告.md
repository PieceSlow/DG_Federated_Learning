# 实验04 报告：医疗病历数据组织汇聚

> 基于 MIMIC-IV、MIMIC-IV-Note 与 UMLS 的多源医疗数据治理
> 数据：100 人真实队列（MIMIC-IV 3.1 / Note 2.2）｜运行：`--llm off`（可复现）+ 10 人 `--llm api`（智能体演示）
> 本报告的数字均来自 `output/` 与 `output_api10/`（患者级产物已 gitignore，不进仓库）。

## 摘要

我们围绕"多中心临床研究协作中的本地 EMR 标准化"场景，把 MIMIC 的 11 张源表与 155 份出院小结
治理成一套**可关联、可理解、可管理、可支持业务**的数据资源：

- **汇聚**：按患者划分 100 人队列（train/tuning/held_out = 78/10/12），产出 MEDS 标准事件仓储
  **148,336 条事件、3,892 个编码、14 个命名空间**，统一事件表 24,554 行、患者 360 100 行；
- **对齐**：4 个匹配器 + 组合器 + 约束执行器 + 选择器，得到 **38 条字段映射**（auto 22 / review 16），
  并用映射**生成 SQL**（87 行），SQLite 逐列对账 **42 列 0 差异**；
- **对象化**：8 类对象、9 条关系，对象图谱 **27,392 节点 / 49,412 边**；
  多智能体链条（ObjectFinder → RelationExtractor → 本地执行 → GraphCritic）在真实 API 下建出
  8 类/9 关系，成本约 **$0.03/轮**，并有逐条 trace；
- **概念**：UMLS 2026AB 归一，覆盖率 **84.3%**，概念节点 **2,262（CUI 2,042 + 编码级 220）**，
  标签概念与图谱命中率 **99.96%**；
- **标签**：L1–L4 共 **136,732 条、19 个 tag_key**，含否定状态/确定性、CUI/语义类型；
- **分级与目录**：8 条分级规则、7 条落地结果，五级目录（2 资源 / 8 资产 / 4 服务 / 2 共享 / 3 开放），
  并有**动态调整**：级别配置化、分级历史、复核检测器；
- **业务闭环**：心衰 30 天再入院（32 人、7 例、21.9%），证明从"对象+标签"能直接生成业务视图。

## 1. 场景、主体划分与总体设计

### 1.1 场景

多家医院各自保有原始 EMR，原始病历不集中共享；每个节点先在本地完成对象治理与标准化，
再把允许流通的资源描述、受控统计或模型参数用于协作研究（对应 `Lab3` 场景与本实验"数据源模拟"要求）。

### 1.2 按主体划分（任务一.1）

以 **Patient 为聚合根**按患者拆分数据空间，每名患者一个 `subject_id`；训练/调优/留出按患者划分，
避免同一患者跨集合造成泄漏。

| 主体 | 承载表 | 数据内容 | 行数（100 人） |
|---|---|---|---|
| Patient | `patients` | 人口学 | 100 |
| Encounter | `admissions` | 住院时间、类型、死亡标志 | 350 |
| ICUStay | `icustays` | ICU 入出科、护理单元 | 126 |
| Diagnosis | `diagnoses_icd` | ICD 诊断编码 | 5,319 |
| Procedure | `procedures_icd` | ICD 操作编码 | 696 |
| Prescription | `prescriptions` | 药品、剂量、途径 | 18,384 |
| ClinicalNote | `discharge`（Note） | 出院小结文本 | 155 |
| （检验） | `labevents` | 检验项目与数值 | 118,075 |
| （字典） | `d_labitems` / `d_icd_*` | 编码描述 | 1,650 / 112,107 / 86,423 |

划分依据：患者是跨表关联的稳定主键；按患者划分可保证"同一人的事件不跨集合"，且与联邦学习的
"节点内数据不出域"一致。选择依据与局限见 `docs/01`。

### 1.3 12 阶段流水线

```text
01 接入 → 02 组织标准化 → 03 质量校验 → 04 事件仓储 → 05 多源汇聚 → 06 字段对齐
→ 07 概念归一 → 08 对象化 → 09 标签化 → 10 分类分级 → 11 编目 → 12 质量报告
```

每阶段产物落盘，`run_summary.json` 记录阶段耗时；`audit/audit_log.csv` 记录每步做法；
`--llm off` 全流程确定性可复现。

## 2. 数据汇聚（任务一.2）

### 2.1 做了什么

- **结构化**：从 11 张表按队列患者分块扫描（大表 `prescriptions`/`labevents` 采用"分块 + 排序探测提前停止"），
  统一时间列 dtype，保留原始 `subject_id/hadm_id/stay_id` 以便对账；
- **文本**：读取 155 份出院小结，按章节头切分，用确定性规则抽取诊断/用药行（**不调用大模型**，
  规则见 `governance/text_extraction.py`）；
- **标准化**：把源表映射成 **MEDS** 标准事件（`subject_id/time/code` 必填 + 数值/文本可选），
  编码统一为 `命名空间//值`（如 `DIAGNOSIS//ICD9//5723`、`LAB//MIMIC_ITEM//50912`）。

### 2.2 结果

| 指标 | 数值 |
|---|---|
| MEDS 事件 | **148,336**（11 类事件 × 14 个命名空间） |
| 唯一编码 | 3,892 |
| 统一事件表 `clinical_events` | 24,554 行（诊断 5,319 / 处方 18,384 / 操作 696 / 文书 155） |
| 患者 360 | 100 行 |
| 患者划分 | train 78 / tuning 10 / held_out 12 |

### 2.3 质量校验（任务一要求"数据质量统计"）

- MEDS Schema 校验：必填列、类型、时间可解析；去重 22 条、孤立 `hadm_id`/`stay_id` 0 条；
- 写盘后**重新读回**并做 5 项规范校验（防止写出非法 parquet）；
- 质量规则共 8 类，最终 **error 0 / warning 925**（构成见 §9）。

## 3. 数据对齐（任务一.3，对应《数据对齐》课件的"必展示"点）

`Lab4/数据对齐.md` 的核心要求：**同命不同义、同义不同名、无名需推**；字符串/集合/分布相似度；
模式匹配系统（多匹配器 + 组合 + 约束 + 选择）；一对多要转换函数；粗筛 + 精排 + 验证 + 修正；
"按需给数据"而不是一股脑；最后生成 SQL。下面逐条对照我们的实现。

### 3.1 同命不同义 / 同义不同名 / 无名需推

| 情形 | 我们在数据里遇到的例子 | 处理 |
|---|---|---|
| **同命不同义** | `hadm_id` 与 `stay_id` 都叫"id"，但前者是住院、后者是 ICU 停留；`subject_id` 在患者表是主键、在事件表是外键 | 先定"表粒度 + 主键"，再允许 join；`stay_id` 只通过 `icustays.hadm_id` 挂接（`link` 类映射），不允许直接当 `hadm_id` |
| **同义不同名** | `drug`（处方）与 `label`（检验字典）都可读名；`icd_code` 在诊断表与操作表语义域不同 | 名字规范化 + 同义词表（`label/title/name/display/drug` 归一），并用"目标字段 × 源表"隔离，避免跨域误配 |
| **无名需推** | 目标字段 `event_time` 在源表没有同名列 | 按事件类型**派生**：诊断=无时间（留空）、操作=`chartdate`、处方=`starttime`、文书=`charttime`（`derived_fields.yaml` + `template/uses`） |

### 3.2 相似度：我们用了哪几种

| 课件提到 | 我们是否使用 | 实现 |
|---|---|---|
| 字符串相似度（编辑距离） | ✅ | `SequenceMatcher` + token Jaccard（`alignment/matchers.py`） |
| 集合/向量 | ✅（集合） | 名称 token 集合的 Jaccard；未做向量嵌入 |
| 分布距离（KL 等） | ❌ | 未用；值域匹配只用"类型族 + 空值率"的本地统计，避免发送取值 |
| 类型/结构 | ✅ | 类型族（int/float/text/日期）；共同后缀（`_id/_time/_code`）加权 |
| 图相似度 | ❌ | 未做（对象层关系靠规则与智能体提案，不做图编辑距离） |

**说明**：没做的部分在报告里如实写，不宣称"全用了"。

### 3.3 模式匹配系统：4 个匹配器 + 组合 + 约束 + 选择

```text
目标字段（8 个）× 源表字段
   ├─ 名称匹配（0.45）：token 化 + 同义词 + Jaccard/SequenceMatcher
   ├─ 类型匹配（0.25）：类型族一致 1.0，int/float 0.8，text 0.3，否则 0.1
   ├─ 结构匹配（0.15）：共同后缀（_id/_time/_code）优先
   └─ 值域匹配（0.15）：本地聚合（类型族 + 空值率），不发送任何取值
        ↓ 组合（加权）
     相似度矩阵（每个目标字段一行、每张源表一列）
        ↓ 约束执行器（声明契约：required/类型/来源合法性）
        ↓ 匹配选择器（每个「目标字段 × 源表」取 top-3，再全局 rank）
```

- 组合权重：0.45 / 0.25 / 0.15 / 0.15（见 `alignment/combine.py`）；
- 约束：`target_schema.yaml` 声明字段是否必填、类型、允许来源；`meds_targets.yaml` 声明每列的
  `source ∈ {spec, derived, mapping, none}`，**声明与实现不一致会被 `check_events` 抓到**；
- 选择：每个目标字段对每张源表保留 top-3 候选，最终人工/契约决定；**不是"取最高分就接"**。

### 3.4 一对一 / 一对多（转换函数）

- **一对一**：如 `code` ← `diagnoses_icd.icd_code`；
- **一对多**：一个目标字段 `event_time` 要按事件类型取不同源列，这是"一对多"，需要**转换函数**。
  我们的做法是"按事件类型分支 + 声明模板"：

```yaml
# derived_fields.yaml（节选）
event_time:
  Diagnosis: null              # 源表无时间，留空（不臆测）
  Procedure: procedures_icd.chartdate        # 日期精度
  Prescription: prescriptions.starttime      # 时间戳
  ClinicalNote: discharge.charttime
```

- 接口层还有 `template` + `uses` 的模板（如 `MEDICATION//{drug}`），也属于"一对多转换"的实现；
- **没做的**：任意用户自定义函数（如单位换算、复合键拼接），目前只支持模板/分支，避免不可控代码执行。

### 3.5 粗筛 → 精排 → 验证 → 修正（反馈）

1. **粗筛**：名称/类型先缩小候选（每目标字段只保留分数过线的源表）；
2. **精排**：结构/值域重排，得到 38 条映射（auto 22 / review 16）；
3. **验证**：用映射**生成 SQL** 并在 SQLite 执行，逐列对账（42 列 0 差异）；
4. **修正**：`review` 项人工确认；映射被 SQL 消费的记 `consumed=True`（19/38），
   未被消费的留在台账里（字典/派生字段不需要 SQL 取）。

**反馈用于训练？** 课件提到"粗筛到精排的反馈可以做训练"。我们**没有训练模型**：
review 结果目前只是人工裁决记录，尚不能自动回归到权重；这是明确的下一步。

### 3.6 "按需给数据" vs "一股脑给模型"

- **按需**：对齐智能体（`--llm api` 时）只拿到**字段元数据**（表名/列名/类型/空值率），
  **不发送任何患者行**；prompt 里明确"输入不含患者行"。
- **对比证据**：单次让一个 LLM 提全量映射时，trace 里只稳定给出 **8 条**；
  结构化匹配器给出 **38 条**（22 auto），且每条都有四个分项得分可解释。
  这就是课件里"不能一股脑都给智能体"的直接证据。
- 我们也没有让 LLM 决定最终映射：LLM 只做"候选建议"，约束执行器与 SQL 对账说了算。

### 3.7 字段映射表（任务一要求）

`output/governance/mapping/field_level.csv`（38 行 × 18 列）字段：

| 列 | 含义 |
|---|---|
| `target_table / target_field / target_dtype / required` | 目标（MEDS 事件表） |
| `source_table / source_field / source_dtype` | 来源 |
| `string_score / type_score / structure_score / value_score / score` | 四个匹配器与组合分 |
| `rank / table_rank` | 候选排序 |
| `method` | `matcher`（31）/ `declared`（7） |
| `status` | `auto`（22）/ `review`（16） |
| `consumed` | 是否被 SQL 消费（19） |
| `evidence` | 依据摘要 |

### 3.8 生成 SQL（课件标注 ★ 的"组织汇聚重要模块"）

`output/governance/mapping/build_clinical_events.sql`（87 行），结构是"每类事件一个 CTE + UNION ALL"：

```sql
WITH dx AS (SELECT subject_id, hadm_id, 'Diagnosis' AS event_type, ...
            FROM diagnoses_icd),
     px AS (... FROM procedures_icd),
     rx AS (... FROM prescriptions),
     note AS (... FROM discharge)
SELECT * FROM dx UNION ALL SELECT * FROM px ...
```

- 生成逻辑：`mapping_usage` 记录每条映射落在 SQL 的哪一段；
- 对账：执行后行数 24,554 与事件表一致，**42 列逐列非空数 0 差异**；
- `consumed` 列如实标出 19/38 被消费，其余 19 条是"字典/派生/无需 SQL"的映射（不是坏了）。

|---|---|---|---|---|---|
| Patient | subject_id | gender, anchor_age, anchor_year | patients | L3 | 100 |
| Encounter | hadm_id | admittime, dischtime, admission_type, hospital_expire_flag | admissions | L3 | 350 |
| ICUStay | stay_id | intime, outtime, first/last_careunit | icustays | L3 | 126 |

### 4.2 类图与边（"边也当成表存"）

- 类图：`output/graphs/graph_classes.png`（8 类 9 关联，字段/主键/敏感级/实例数）；
- 边表：`output/governance/graph/edges/*.parquet`，**每条关系一张表**，字段
  `src_type / src_id / dst_type / dst_id / relation / evidence / confidence`；
- 规模：**27,392 节点 / 49,412 边**（100 人）。

### 4.3 多智能体链条（课件要求"图谱背后有一系列智能体"）

```text
ObjectFinder（看 schema/统计，提对象）
  → 代码校验（表存在、主键在列、主键唯一）
  → RelationExtractor（提关系）
  → 代码校验（on 必须是主键、join 列存在）
  → 本地 build_graph 执行
  → GraphCritic（看图谱统计，提缺陷；可回退修正一轮）
```

**真实 API 实测**（10 人，`deepseek-chat`）：ObjectFinder 提 7 类对象、RelationExtractor 提 6 条关系、
GraphCritic 重试 1 次 → **8 类对象 / 9 条关系**，成本约 **$0.03**；`audit/agent_trace.jsonl`
逐步记录 `agent / step / decision / tokens / duration`，可逐条审计。

关键设计：**LLM 提议，代码执行**。不合法提案会被驳回重试；`--llm off` 时整体回退到
`objects.yaml`，保证可复现。

### 4.4 四能力对照（课件 L66：能更新、能治理、对上支持业务、对下管理数据）

| 能力 | 我们做到的 | 还差的 |
|---|---|---|
| **能更新** | 实例层 `incremental`（delta 统计）；**模式层 overlay**：新增对象经 `scripts/propose_object.py` 校验后写入 `objects.local.yaml`，下次自动生效（演示：加入 LabEvent → 9 类/10 关系、17,051 节点）；**分级层**：级别配置化 + 历史 + 复核检测器 | 新表仍需 ingest 加载；对象发现靠人触发 |
| **能治理** | 图谱写实校验（重复节点/孤立节点/时间冲突）、概念层归一、标签与图谱口径告警、复核检测器 | 图谱是质量问题的"暴露方"，不是发现方；没有靠图谱猜未知语义 |
| **对上支持业务** | 心衰 30 天再入院场景（32 人/21.9%），对象+标签→业务视图；L1–L4 标签 | 没有从业务问题倒推对象模型的显式流程；依从性等业务标签缺数据 |
| **对下管理数据** | 对象清单、字段级 38 条映射 + 记录级映射、8 条分级规则、五级目录、共享边界 | 元数据没有独立管理系统；目录是生成式，未接动态维护 |

### 4.5 质量发现（课件 L64 的思考题）

图谱能暴露的问题（`governance/graph/verify.py`）：

- `GRAPH_DUPLICATE_NODE`：同一对象重复建节点（我们靠它发现了主键缺列）；
- `GRAPH_ORPHAN_NODE`：对象没有边（关联缺失）；
- `GRAPH_TEMPORAL_CONFLICT`：边的两端时间不一致（实测 1 条）；
- `LABEL_GRAPH_MISMATCH`：标签口径与图谱口径不一致。

**诚实结论**：这些规则能发现"结构性"问题（关联缺失、重复、时序矛盾），但**发现不了**
编码错误、单位错误这类语义问题——那要靠 UMLS 映射和人工 review。所以我们不说"图谱能自动治理质量"。

## 5. 数据标签化（对应《对象化和标签》课件）

### 5.1 标签体系

```text
业务（场景/随访）
   ↑ 标签支撑
标签（KV，打在对象上）
   ↑ 基于
图谱（对象/关系）
   ↑ 来自
数据（clinical_events / 源表）
```

- 19 个 `tag_key`、**136,732 条**标签，全部落在 `object_labels.parquet`；
- L1 敏感/共享、L2 记录级（实体类别、时间精度、缺失原因、**断言**、**确定性**、年龄/住院天数）、
  L3 概念级（`code_system`、`semantic_type`、`cui`）、L4 患者级（共病负担、多重用药、频繁住院、
  用药强度、随访优先）；
- 标签要求"介于数仓和数据集市之间"：我们以 `clinical_events`（数仓层）为输入，产出患者/对象级
  KV（数据集市层），见 `labels/definitions.yaml` 的规则口径。

### 5.2 医学标签强化（UMLS）

- 编码 → CUI：覆盖率 **84.3%**（ICD10 99.6% / ICD9 94.4% / ICD10PCS 99.4% / RXNORM 88.8% / LNC 39.8%）；
- `L3.cui` **2,042 条**、`L3.semantic_type` 取 UMLS STY；未命中的编码降级为编码级身份（不猜）；
- 标签概念对象与图谱概念节点对账：**99.96%**（差 1 条文书概念）。

### 5.3 否定状态与确定性

- 从文书规则抽取 `assertion`（present/negated/historical/hypothetical/family），同一文书取最强；
- 实测：present 24,548 / historical 4 / negated 2；`L2.certainty` 全为 definite
  （数据里没有"疑似"表述）——**维度建了，但数据本身罕有**。

### 5.4 手动 / 自动 / 半自动

- 自动：`labels/engine.py` 按 `definitions.yaml` 规则批量计算；
- 半自动：`review`（映射）与人工确认（新增对象）留在流程里；
- 手动：支持 `--manual-labels` 覆盖（把"隐性知识显性化"，如临床对某标签的修正）。

### 5.5 业务驱动的边界

课件例子"重度高血压 + 不爱吃药 → 分配随访资源"：我们做得出一半——共病/多重用药/随访优先有，
**依从性没有数据源**（MIMIC 没有服药记录），不能造这个标签。这属于"业务驱动标签"，下一步要接数据。

### 6.2 动态调整（任务二.4）

| 触发源 | 判断问题 | 动作 | 生效方式 |
|---|---|---|---|
| 数据内容变化（新表/新列/自由文本） | 是否新增类别、级别是否升？ | 加/改规则 | 改 `levels.yaml`/规则 → 重跑 → 历史记 diff |
| 使用目的变化（科研→发布） | 原级别能否支持？ | 收紧/放开限制 | 改规则 → 编目/共享边界跟随 |
| 共享范围变化 | 满足 k≥10、去标识？ | 调整开放项 | 改共享目录 + 重跑 |
| 风险阈值变化（k 10→5） | 聚合项还能开放吗？ | 重评 C07 | 改阈值 → 重跑 |
| 数据删除/过期 | 资产还在吗？ | 移除类别 | 改规则 → 重跑，历史保留 |

已实现的三个机制：

1. **级别配置化**：`governance/levels.yaml`（C01–C08），`classify` 与 `labels` 共用 `level_of()`；
   实测把 C08 从 L3 改 L2，`result.csv`、`Dataset:patient_360` 标签、历史 diff、复核信号四处同时变；
2. **分级历史**：`classification/level_history.jsonl`（时间/规则版本/规则指纹/各级别/diff），只追加不覆盖；
3. **复核检测器**：`classification/review_required.json`（新表、新列、疑似自由文本、级别变化），
   基线只存表→列；第一次运行只建基线。
