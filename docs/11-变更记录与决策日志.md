### 1. 决策：MEDS 接口由"声明驱动"，不再硬编码

- **背景**：`standardize.py` 有 6 段手写循环产出事件，`meds_targets.yaml` 只是旁边一张手写
  `source_hint` 的对照表；两者长期不一致（`DIAGNOSIS.time` 声明 required 却一直发 NULL、
  `DEMOGRAPHIC` 发了没声明、`LAB.code` 模板与实现不同、`MEDICATION` 剂量声明了却发空），
  且没有任何检查能发现。
- **决定**：`meds_targets.yaml` 作为接口**唯一声明**，`standardize` 按声明产出事件；
  新增 `alignment/interface.py` 做"声明 × 匹配结果 × 实际事件流"三方核对。
- **改了什么**：
  - 声明里每列写 `source ∈ {spec, derived, mapping, none}`，编码用 `template` + `uses`，
    关联用 `on_column`（YAML 1.1 会把裸 `on:` 解析成布尔 `true`）；
  - 删掉 `_map_structured`，改 `_emit_interface_events`；`_check_declared_columns` 在运行前
    校验声明引用的列真实存在；
  - `crosswalk.py` 产出 55 行接口台账（`resolved_by ∈ mapping/spec/derived/none/unmapped`）；
  - `sql.py` 的 `stay_id` 归 `link`（ICU 时间窗）、`split/icd_chapter` 归 `postprocess`，
    对账从"只比行数"升级为"逐类型行数 + 逐列非空数"。
- **影响**：接口从"装饰性对照表"变成可执行契约；台账 `unmapped` 从"看不出"变成 0 可验证。
- **验证**：100 人队列 `unmapped` 0、未声明命名空间 0、必填违规 0；SQL 42 列 0 差异；
  `tests/test_meds_interface.py` 22 条。
- **遗留**：操作已补（见下条）；`LAB` 文本 `value` 未接入（`source_gaps` 已写补法）。

### 2. 决策：补 `PROCEDURE` 事件类型

- **背景**：操作只在 `clinical_events`（内部宽表）里，对外事件流没有；而图谱早就有
  `Procedure` 节点与 `has_procedure` 边——"对内是一等对象、对外看不见"。
- **决定**：事件清单是**本组自定**的，补这一类不涉及外部约束；按 `PROCEDURE//ICD{v}//{code}`、
  时间取 `chartdate`、字典校验 `d_icd_procedures`。
- **影响**：事件 147,640 → **148,336**；编码 3,558 → **3,892**；命名空间 13 → **14**；
  接口 10 类 → **11 类**（台账 50 → 55 行）；多出 3 条 `TEMPORAL_INCONSISTENCY`

- **验证**：SQL 对账不变（24,554 行、42 列 0 差异）；`clinical_events` 不含操作不受影响。

### 3. 决策：可信边界区分"有出处"与"本组自定"

### 5. 决策：图谱对象主键必须能区分"一行数据"

- **背景**：系统核对发现 20 人队列 7,424 个节点只有 6,935 个唯一 id（处方重复 486、诊断 3）；
  `has_prescription` 4,267 条边只有 3,781 个唯一三元组；增量模式 `delta.updated = -489`。
- **根因**：`diagnoses_icd.seq_num` 和 `prescriptions.pharmacy_id` 都不唯一
  （同序号多条诊断码；一个 `pharmacy_id` 下多个药品组分），而 `objects.yaml` 把它们当主键。
- **决定**：诊断键加 `icd_code`、处方键加 `drug`；新增 `GRAPH_DUPLICATE_NODE`（error）自检；
  `store._compare` 比较前按主键去重。
- **影响**：100 人 28,020 节点全部唯一；增量 delta 恢复为 `updated 0 / unchanged 7,424`；
  `--llm mock` 的提案主键同步修正（否则 mock 会报 3 条 error）。
- **验证**：真实数据 6.36M 行诊断加列后零重复；处方 2M 行加 `drug` 后仅剩 120 行完全重复
  （属真实重复行）；`GRAPH_DUPLICATE_NODE` 0。

### 6. 决策：图谱与标签共用「事件编码 → UMLS 概念」解析

- **背景**：接入 UMLS 2026AB 后 `graph_ratio` 只有 **49.65%**：图谱按 UMLS 源体系查
  （操作 `ICD10PCS`、药品 `RXNORM`），标签按事件 `code_system` 查
  （操作 `ICD10`、药品 `MIMIC_FORMULARY`），操作和处方永远 join 不上；且图谱在 UMLS 模式下
  只保留映射成功的编码，未映射的编码不建节点。
- **决定**：新增 `ConceptResolver`，按事件类型对齐体系名（诊断 `ICD{v}`、操作
  `ICD10PCS/ICD9CM_PROC`、处方按药名查 `RXNORM`）；**命中用 CUI，未命中建编码级兜底节点**；
  图谱与标签调同一个解析器和 `concept_object_id`。
- **影响**：
  - 概念节点 1,952 → **2,453**（CUI 1,948 + 编码级 505）；
  - 标签概念对象 2,727 → **2,454**（CUI 合并后变少）；
  - `graph_ratio` 49.65% → **99.96%**（差 1 条文书概念）；
  - `L3.cui` 1,354 → **1,948**；操作概念 0 → 272 个编码、处方概念 0 → 615 个编码；
  - 告警 444 → **1,157**（增量全是 `CONCEPT_UNMAPPED` 713）。
- **验证**：`tests/test_concept_key.py` 新增 5 条 resolver 用例；`tests/test_umls.py` 断言
  "有编码的事件节点必有概念边"、"标签概念对象 ⊆ 图谱概念节点（除文书）"；
  100 人产物交叉核对 42/42 通过。
- **遗留**：药品/检验映射率偏低（RXNORM 54.5%、LNC 39.8%）；`output/umls_cache/` 不入库，
  首次需要 `python -m governance.umls.preprocess`（约 2 分钟，1.2M 概念）。

### 10. 决策：跑真实 LLM（api）并修两个真实缺陷（后续见 #11）

- **背景**：mock 是固定返回，答辩若被问"智能体真的这么决策吗"无法回答；需要一次真实调用。
- **实测（10 人，2026-11-18，`output_api10`）**：7 次调用、4.2 万 tokens、$0.024（≈¥0.17）；
  trace 7 步：Aligner 提 8 条映射 → Verifier 通过；ObjectFinder 提 **10 类对象**；
  RelationExtractor 提 **14 条关系**（两次）。
- **缺陷 1：max_tokens 截断**。默认 1200 时对象/关系 JSON 被截断成空内容
  （`Expecting value: line 1 column 1`），管线静默回退到 `objects.yaml`。已把默认改为 **4000**
  （`LLM_MAX_TOKENS`），空内容时报错带上 `finish_reason`；缓存键加入 `max_tokens`，避免复用截断回复。
- **缺陷 2：复合 join 不支持**。智能体提的 `icd_diagnosis_code_has_diagnosis` 用
  `on: icd_code,icd_version`（复合键），校验器只接受单列主键 → 关系校验失败 → 回退到
  8 类确定性模型。所以 **api 这一轮的图谱实际是 objects.yaml 的模型**，智能体的贡献停留在
  "提案 + 被拒"，不能宣称"图谱由智能体建成"。
- **影响**：docs/00 增加 max_tokens 说明；docs/09 §4.3 记录 api 口径；图与产物在 `output_api10/`
  （gitignored）。
- **遗留**：实现复合 join（RelationSpec 支持多列）后重跑 api，才谈得上"智能体建图"；
  另外应把智能体提案导出为 `graph/agent_proposal.json` 供答辩展示。

### 11. 决策：把"对象范围"写进 prompt，而不是实现复合 join

- **背景**：api 第一轮智能体提了 10 类对象/14 条关系，其中 `icd_code,icd_version` 复合 join
  被校验器拒掉，回退到确定性模型。问题：要不要支持复合 join？
- **判断**：复合键本身有意义（我们自己的 Diagnosis 主键就是 `subject_id+hadm_id+seq_num+icd_code`），
  但**复合 join 的目标是 ICD 字典表**——字典表在我们模型里是"参考数据"，不是图谱对象；
  为它实现多列 join 得不偿失。正确做法是**约束对象范围**，让智能体别提字典/参考表。
- **改动**：
  - `object_finder` prompt：给允许清单（Patient/Encounter/ICUStay/Diagnosis/Prescription/
    Procedure/ClinicalNote），禁 `d_*` 字典表与 `labevents`；主键必须唯一（附
    `pharmacy_id`/`hadm_id` 反例）；
  - `relation_extractor` prompt：`on` 必须是单列、对象名用清单名；
  - 校验器：新增主键唯一性检查（≤50 万行时执行）；对象校验搬进 Supervisor，
    不通过会带 feedback 重试；
  - `_node_frame`：把主键列并入节点属性（智能体把 `icd_code` 放在 keys 里，否则概念层取不到）。
- **结果**：智能体模型落图——ObjectFinder 提 7 类对象、RelationExtractor 提 6 条关系，
  GraphCritic 重试 1 次；最终 **8 类对象（含派生 Concept）/ 9 条关系**，与 canonical 一致。
  关系名由 `canonical_relation_name` 按 (from,to) 兜底改名，prompt 同时要求 `has_note` 等固定名。
- **踩坑**：强制 ClinicalNote 后，模型给 `keys: []`（不知道 discharge 主键），校验器直接拒绝；
  prompt 里补上"ClinicalNote 主键就是 note_id"后才通过。
- **遗留**：每次新增数据源仍要人工改"允许对象清单"（词表是代码资产，不是模型自发现）。

### 13. 决策：动态新增对象用 overlay，不直接改 objects.yaml

- **背景**：笔记 L49 要求"数据/需求不断加入，图谱动态新增"；之前只有实例层增量，
  新对象要改 `objects.yaml`，没有校验、没有确认记录。
